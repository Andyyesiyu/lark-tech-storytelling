常驻沙箱的平滑热切与长连接防串号设计

核心命题：如何让常驻容器在不中断活跃会话的前提下秒级升级，又避免长连接复用因偶发超时陷入“全员串号”？

本文用两个物理模型拆解背后的工程契约：指针原子拨动（升级面）与信封钢印配对（传输面）。

1. 升级面：拨动软链指针，而不是推倒整座容器

把运行时写死在容器镜像里，意味着哪怕只改一行代码，都必须销毁整台实例重拉镜像——活跃长连接瞬间断流。

平滑热切的核心是不动容器底座，只在磁盘上并排准备好新版目录 v1.5，校验通过后执行一次内核级原子的 rename() 把 current 指针瞬间拨向新舱，同时让旧舱把存量连接自然排空后再熄火。

阶段 ① 静默落盘：v1.4.2 正常承接全部会话，v1.5.0 在旁路目录独立下载校验，零锁竞争。

2. 传输面：当信封没有编号，一次超时就会让整条履带错位

长连接保住了，但为什么线上偶发一次 200ms 抖动，后续几十个请求全都拿到了驴唇不对马嘴的结果？

看下方这条真实的传送履带：当 #1 蓝席位 因超时提前撤离窗口，排在后面的 #2 紫席位 自动补位到窗口正上方；然而管道里滑出来的第一封信仍然是 #1 的蓝色迟到回执——没有钢印校验时，紫色席位直接拆开了蓝色信封，此后每一拍全部错位一格。

3. 协议收口：两行校验切断错位传播链

❌ 脆弱实现：按 FIFO 队首盲领 implicit_fifo.ts 
socket.on("frame", (payload) => {
  // 【隐患】一旦前序请求超时提前 shift，
  // 队首 waiter 永远错拿到前一个人的旧包
  const waiter = pendingQueue.shift();
  waiter?.resolve(payload);
});
✓ 收敛实现：按 req_id 寻址 + 孤儿帧自净 mux_channel.ts 
socket.on("frame", ({ reqId, payload }) => {
  const waiter = inflightMap.get(reqId);
  // 【自愈】超时已移除的迟到帧直接丢弃，零串号
  if (!waiter) return metrics.inc("stale_drop");
  inflightMap.delete(reqId);
  waiter.resolve(payload);
});
